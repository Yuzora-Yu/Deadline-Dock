## 実装済み

1. OAuth PKCE/state/loopback認証、Windows資格情報へのsecret/refresh token保存、専用シート作成、URL操作、解除と再接続。
2. タスクの初回送信・双方向差分同期。UUIDで照合し、行順には依存しません。IDのない新規行はIDを先に確定してから取り込みます。
3. 件名・説明・分類名・期限・状態・表示開始の同期。期限の内部データを隠し列Nに保存し、「明日」等の期限が同期日ごとに動くことを防ぎます。
4. 両側変更の競合比較とローカル／Google側の採用。比較後に内容が変われば再確認。削除済みローカルをGoogle側から戻す場合は明示して選択。
5. SQLiteトランザクションとrevision照合、Google Sheets由来のactor付き変更履歴、ローカル削除のtombstone送信。
6. 60/120/300秒の自動同期、変更後の遅延同期、フォーカス／オンライン復帰、手動同期、通信失敗時の段階的な再試行。
7. 既存の専用シート候補を検索・選択、新規シート作成による復旧。以前のシートは削除しません。
8. Sheets書き込み前の影響行と変更予定をSQLiteの `sync_write_journal` に記録。応答喪失時に同一編集を再送する前に再読込して照合。
9. JSON復元時に同期と基準値を停止・クリアし、古いrevisionを使った誤同期を回避。復元後は内容を確認して再接続してください。

## 別PCから再開する

WindowsでGit、Node.js/npm、Rust MSVC、Visual Studio C++ Build Tools、WebView2を用意し、次を実行します。Pythonは検証・ZIP作成に使います。

```powershell
git clone https://github.com/Yuzora-Yu/Deadline-Dock.git
cd Deadline-Dock
npm ci
npm run check
npm test
python scripts/validate.py
cargo test --manifest-path src-tauri/Cargo.toml --lib -j 2
npm run tauri build -- --bundles nsis
```

開発起動は `npm run tauri dev`。生成先は `src-tauri/target/release/deadline-dock.exe` と `src-tauri/target/release/bundle/nsis/`。自動ビルドCIやGitHub Releaseへのバイナリ配布は設定していません。

Google設定は [GOOGLE_SHEETS_SETUP.md](GOOGLE_SHEETS_SETUP.md) を参照してください。**認証用ブラウザはDeadline Dockを実行しているPCで開く必要があります。** 戻り先は127.0.0.1なので、別PCだけで同意しても元PCのアプリへ返せません。手元の別Windows PCでクローン・起動して、そのPCで設定・同意すれば進められます。

Windows資格情報はPCごとです。Gitのクローンでは実タスクも認証状態も移りません。既存タスクの移行が必要ならアプリのJSONエクスポート／復元を利用し、復元後に再認証してください。動作中のSQLiteファイルを共有ドライブ上で同時利用しないでください。

元PCの旧アプリが起動中ならトレイの「終了」で終了後に更新版へ切り替えます。ウィンドウ右上の×はトレイへ隠す操作です。アプリID `local.deadlinedock.app` を不用意に変更すると既存DBの参照先も変わるため維持してください。

## 実Google検証の順序

テスト用タスクと専用シートで以下を確認してから実運用へ進んでください。

1. Desktop appクライアント設定、Google同意、メールとシートURL表示、自動シート作成。
2. 初回タスク送信、URLコピー／ブラウザで開く。
3. アプリから件名・期限・状態を変更してシートへ反映。
4. シートから件名・期限・状態を変更してアプリへ反映し、Google由来の履歴を確認。
5. シートのID空欄に新規行を作り、重複せず取り込まれること。行の並べ替え後も同じタスクを更新すること。
6. 自動同期を止めて両側を編集し、競合表示と両方の採用操作を確認。
7. オフライン中の編集、復帰後の同期、API権限エラーの表示とローカル操作継続。
8. アプリ再起動でrefresh tokenが使えること、解除・再接続で既存シートを再利用すること。
9. シートをゴミ箱へ移動した場合のエラー、復元／候補再選択／新規作成による復旧。
10. 別PCからの同時編集、同期途中の終了、バックアップ復元後の再接続。

## 検証結果と限界

- TypeScript同期テスト: 22件成功。UUID・競合・期限・削除・行順変更・不正データ・通信応答喪失・認証等エラーを模擬検証。
- Rustテスト: 10件成功。OAuth、資格情報の試験用エントリー、SQLiteのrevision照合、履歴失敗時のロールバック、固定sheetId、文字列としての安全なセル更新など。
- `python scripts/validate.py`: 59項目成功。`npm run check` / `npm run build` 成功。
- ブラウザの模擬データで同期設定、競合比較表、採用ボタンまでのスクロール、自動同期切替を確認。実データには接続していません。
- 実デスクトップ／実GoogleのE2Eは未確認。前回Windows UI操作ツールは起動ハンドラー準備エラーで失敗しました。
- Rustの最初のテストビルドはOS資源不足で失敗。並列数2、dev debug情報なし・incremental無効で再実行し成功しました。
- `npm run tauri build -- --bundles nsis`: 成功（release 10分44秒）。GUI subsystemと配布用コピーのSHA-256一致を確認しました。

Sheets APIにはこの用途の比較交換（CAS）付き書き込みがありません。書き込み前に再読込して変更を検知し、書き込み後にも検証しますが、その間に発生する他端末の編集との競合を完全には排除できません。書き込み前の記録は復旧調査用です。完全な無損失同時編集を保証した実装とは扱わないでください。

シートの物理的な行削除は警告し、ローカル削除・自動再作成にはしません。ID重複も自動統合しません。送信は1回1000行以下で分割。確定済み書き込み記録は最大20件相当へ整理し、未確定記録は保持します。記録にはタスク内容が含まれるためDBごと非公開で扱います。
